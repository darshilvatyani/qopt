About this guide
This guide explains qopt completely, in one place. It starts with what a database index is, builds
up the ideas the project depends on, walks through the architecture, lists every technology used,
and ends with a line-by-line tour of the most important code and the measured results.
Who it is for
It is written for someone who is new to database performance and to AI tooling, but who can read a little code.
Every term is explained the first time it appears (there is also a glossary in Appendix A). If you already know
PostgreSQL well, you can skip Part I.

The project at a glance
What it is A PostgreSQL slow-query advisor. It finds slow queries, explains why they are slow,
and recommends fixes that it has verified.
Main idea Suggestions from rules and from an LLM (Gemini) are tested against ground truth:
hypothetical indexes (HypoPG) and real experiments on a shadow copy of the
database, inside transactions that are always rolled back.
Built as A TypeScript monorepo: a core engine, a command-line tool, an HTTP API and a
web UI.
Databases Three PostgreSQL 17 instances: target (being tuned), shadow (the lab), meta (qopt’s
own storage).
Headline result On a 15-query demo workload, validated suggestions made the workload 5.2× faster.
The same LLM suggestions applied without validation gave only 1.3×.

CHAPTER 1
Whatis qopt?
qopt looks at a PostgreSQL database, finds the queries that are slow, works out why, and
suggests fixes: new indexes, rewritten queries, better statistics, or a memory setting. What
makes it different is that it never recommends a fix on faith. Every suggestion is tested against
the real query planner and real data first, and only proven improvements reach you.
1.1 The problem it solves
Applications talk to databases through queries: small programs written in SQL, such as “give me the 20 most
recent orders of customer 42”. When a table is small, every query is fast. As data grows, some queries slow down
dramatically. On the demo database used throughout this guide, one query takes about 700 milliseconds; with the
right index it takes 150. Another drops from 95 ms to under 1 ms.
Finding the right fix is expert work. You have to read the database’s execution plan, know which kind of index suits
which kind of filter, and understand how the database estimates costs. It is tempting to ask an AI model instead,
and models are good at producing plausible advice. But plausible is not the same as correct. During this project
the Gemini model made exactly the kinds of mistakes an expert would catch:
It proposed an index on date(created_at) . PostgreSQL refuses that index, because date() of a timestamp￾with-time-zone depends on the session’s time zone.
It proposed a rewritten query that looked equivalent but returned different rows, because it hard-coded a time￾zone offset.
It proposed raising a memory setting for the slowest query. That made the query slower (704 → 735 ms).
It bundled a CREATE EXTENSION statement into what should have been a single index suggestion.
Applied blindly, advice like this wastes time at best and returns wrong answers at worst.

1.3 What makes it different
KEY IDEA
An AI suggestion is a hypothesis. qopt treats it like one: it runs the experiment and keeps the suggestion only
if the evidence supports it. This “generate, then verify” loop turns a text generator into an engineering tool.
Typical “AI for SQL” tool qopt
Returns text that sounds right Returns changes that were measured to work, with the numbers
Cannot tell a wrong rewrite from a right
one
Runs both queries and compares the results row by row
May invent columns that don’t exist PostgreSQL itself rejects them; the error is shown and classified as a hallucination
One-shot answer Rejections go back to the model with the reason, and it tries again
No way to know if it helps An evaluation harness measures hit rate, precision and speedup against known
answers
1.4 What you get
A command-line tool ( qopt ) to set up databases, generate a workload, capture slow queries, analyse them,
ingest documentation and run evaluations.
A web UI showing the slow queries, the analysis progress, every candidate with its verdict, the plan before and
after, and the evaluation results.
An evaluation harness that compares four configurations on 15 queries with known correct fixes. Validated
suggestions made the workload 5.2× faster (5.7× with documentation retrieval). The same LLM suggestions
applied without validation managed 1.3×, because one bad suggestion slowed the heaviest query.

CHAPTER 2
Databases and SQL in ten minutes
This chapter introduces the handful of database ideas the rest of the guide depends on, using
the demo shop database that qopt creates for testing.
2.1 Tables, rows and columns
A relational database stores data in tables. Each table has named columns with a type (number, text, timestamp,
JSON…), and holds any number of rows. qopt’s demo database models a small online shop with six tables and
about 4.2 million rows in total:
customers 100,000 rows
PK id bigint
email text
full_name text
phone text
country text
city text
tier text
created_at timestamptz
orders 600,000 rows
PK id bigint
FK customer_id bigint
status text
created_at timestamptz
total numeric
shipping_country text
order_items 1,800,000 rows
PK id bigint
FK order_id bigint
FK product_id bigint
quantity int
unit_price numeric
events 1,500,000 rows
PK id bigint
FK customer_id bigint
type text
created_at timestamptz
payload jsonb
reviews 150,000 rows
PK id bigint
FK product_id bigint
FK customer_id bigint
rating int
body text
created_at timestamptz
products 30,000 rows
PK id bigint
sku text
name text
category text
price numeric
attributes jsonb

Arrows point from a foreign key (FK) to the primary key (PK) it references. Only primary keys are indexed.
Figure 2. The demo shop schema created by qopt db setup . Each table has only a primary-key index: every other index is missing
on purpose, so there is something to find.
Every table has a primary key (PK), a column whose value uniquely identifies a row: here always id . A foreign
key (FK) is a column that points at another table’s primary key: orders.customer_id says which customer placed
the order. PostgreSQL automatically creates an index for each primary key, but not for foreign keys. Missing
indexes on foreign keys are one of the most common causes of slow queries in real applications, and the demo
reproduces that on purpose.
2.2 Asking questions with SQL
SQL describes what you want, not how to get it. Here are three of the demo workload’s queries, read clause by
clause:
W01 · a customer’s latest orders
SELECT id, status, total, created_at -- the columns to return
FROM orders -- the table to read
WHERE customer_id = 42 -- keep only this customer's rows
ORDER BY created_at DESC -- newest first
LIMIT 20; -- only the first 20

W11 · combining two tables with a JOIN, then grouping
SELECT c.id, count(o.id) AS orders
FROM customers c
JOIN orders o ON o.customer_id = c.id -- match each order to its customer
WHERE c.country = 'NZ' AND c.city = 'Auckland'
GROUP BY c.id; -- one output row per customer
W13 · aggregating 1.8 million rows
SELECT product_id, count(DISTINCT order_id) AS orders
FROM order_items
GROUP BY product_id
ORDER BY orders DESC
LIMIT 10;
Because SQL only says what, the database must decide how: which table to read first, whether to use an index,
how to join, and how to sort. That decision is called the query plan, and it is the subject of Chapter 4.
2.3 PostgreSQL in one page
Server and databases. A PostgreSQL server (also called a cluster) listens on a network port and holds one or
more databases. qopt uses three servers on ports 5433, 5434 and 5435, each with a database called qopt .
Connections and sessions. A program opens a connection and sends SQL. Settings changed with SET apply
only to that session.
Extensions. Plugins that add features, installed with CREATE EXTENSION . qopt relies on five:
pg_stat_statements , auto_explain , hypopg , pg_trgm and vector (pgvector).
System catalogs. PostgreSQL describes itself in ordinary tables such as pg_class (tables and indexes),
pg_index , pg_attribute (columns) and pg_stats (data statistics). qopt reads these to understand your
schema.
Pages. Table and index data is stored in 8 kB pages. Reading a page from disk is the basic unit of work;
recently used pages stay in memory (the buffer cache). Performance tuning is largely about reading fewer
pages.
2.4 Transactions: the idea qopt’s safety is built on
A transaction groups statements so that they succeed or fail as a unit. You start one with BEGIN and end it with
COMMIT (keep the changes) or ROLLBACK (undo everything). Unusually, PostgreSQL can also roll back schema
changes, such as creating an index. That is called transactional DDL (DDL means statements that change
structure, such as CREATE INDEX ; DML means statements that change rows, such as UPDATE ), and qopt depends
on it:
An experiment that leaves no trace
BEGIN;
CREATE INDEX ON orders (customer_id); -- really built, on the shadow copy
EXPLAIN ANALYZE SELECT … WHERE customer_id = 42; -- measure with the index
ROLLBACK; -- the index never existed
Two refinements appear in the code. A savepoint ( SAVEPOINT name … ROLLBACK TO SAVEPOINT name ) undoes part
of a transaction; qopt uses one around each timed run, so that even an UPDATE sees identical data every time. A
read-only transaction ( BEGIN READ ONLY , or SET transaction_read_only = on ) makes PostgreSQL refuse any
write, which is how qopt runs model-written SQL safely.

CHAPTER 3
Why queries get slow,and how indexes help
Most slow queries read far more data than they need. An index lets the database jump straight to
the rows it wants. This chapter explains the index types qopt can recommend, and the problems
indexes cannot fix.
3.1 The full table scan
Without a suitable index, the only way to answer WHERE customer_id = 42 is a sequential scan: read every row of
orders and keep the ones that match. It is like finding a name in a phone book whose pages are in random order:
you must read the whole book. The cost grows with the table, whatever the size of the answer.
Sequential scan
no usable index
WHERE customer_id = 42
reads every row: 600,000
keeps 8 of them
≈ 10 ms, and it grows
with the table
Index scan
B-tree on customer_id
root page
leaf: 1–39 leaf: 40–60 leaf: 61–…
table pages
≈ 3 page reads, then only the 8 matching rows: ≈ 0.01 ms
Figure 3. W01 on the demo data: the scan reads 600,000 rows to return 8 (about 10 ms). With a B-tree on customer_id , the same
query reads a few pages (about 0.01 ms).
3.2 B-tree indexes

3.4 Indexes that avoid sorting and table visits
Avoiding a sort. If the index order matches ORDER BY , the database reads entries in order and stops after
LIMIT rows. W14 (deep pagination) drops from 53 ms to 4.6 ms with an index on created_at .
Index-only scans. If every column the query needs is in the index, PostgreSQL can skip the table entirely.
INCLUDE (col) adds extra columns to the leaf entries without making them sort keys; that is a covering index.
This works fully only when the table’s visibility map says pages are “all visible”, which VACUUM maintains. qopt
flags index-only scans that still visit the heap (finding HEAP_FETCHES ).
3.5 Expression and partial indexes
An expression index indexes the result of a function. W03 searches WHERE lower(email) = lower('…') ; a plain
index on email is useless because the query compares lower(email) . An index on (lower(email)) matches
exactly (17 ms → 0.01 ms).
WATCH OUT
Index expressions must be IMMUTABLE: always the same output for the same input. date(created_at) on a
timestamptz column is not, because the calendar date depends on the session time zone. PostgreSQL
refuses such an index. Both qopt’s rule-based advisor and Gemini suggested it for W10, and validation caught
it both times. The correct fix is to rewrite the filter as a range
( created_at >= '2026-03-30' AND created_at < '2026-03-31' ).

3.9 Slowness that indexes do not fix
Sorts and hashes that spill to disk. Each sort or hash may use work_mem of memory (4 MB by default). Beyond
that it writes temporary files, shown in plans as Sort Method: external merge Disk: 45808kB . Raising
work_mem for one session can help, but not always: for W13 it made no real difference.
Non-sargable predicates. A filter that wraps a column in a function ( date(created_at) = … ) cannot use a
plain index on the column. (“Sargable” means “can use a search argument”, i.e. an index.) The fix is a rewrite or
an expression index.
NOT IN (subquery) . Besides being hard to optimize, it has a surprising meaning: if the subquery returns a
single NULL , NOT IN returns no rows at all. NOT EXISTS is usually what was meant, and the planner can
execute it as an efficient anti-join. The two are equivalent only when the column can never be NULL , which is
why qopt compares results on real data before trusting such a rewrite.
Deep OFFSET . OFFSET 50000 LIMIT 50 still produces and throws away 50,000 rows. An index helps; “keyset
pagination” ( WHERE created_at < last_seen ) avoids the waste, but it changes the application, so qopt only
mentions it.
OR across different columns. email = … OR phone = … cannot use a single index. With one index per column,
PostgreSQL combines them with a BitmapOr. An index on only one of the two columns does not help at all.

4.4 Cost: the planner’s currency
The planner compares plans using an abstract cost. Roughly, reading a page sequentially costs
seq_page_cost = 1 , reading a page at a random position costs random_page_cost = 4 , processing a row costs
cpu_tuple_cost = 0.01 , and evaluating an operator costs cpu_operator_cost = 0.0025 . A worked example with
the real demo numbers: orders has 600,000 rows in 6,184 pages, so a sequential scan with one filter costs
6,184 × 1 + 600,000 × 0.01 + 600,000 × 0.0025 = 13,684
That is exactly the cost PostgreSQL printed for the scan of orders in W09. An index scan instead costs a few
random page reads per matching row, so the planner prefers it when few rows match. It can only make that call
correctly if it knows how many rows will match. That knowledge comes from statistics.

nested loop expecting 79 rows and then execute it 1,144 times. Extended statistics
( CREATE STATISTICS … (dependencies, mcv) ON country, city ) teach the planner about correlated columns.
qopt validated exactly this fix for W11: the estimate error dropped from 14× to 1.8×.
4.7 Self time, loops and parallel workers
Actual Total Time for a node includes its children, and it is an average per loop (a node inside a nested loop may
run thousands of times). To find where time really goes, qopt computes each node’s self time: total time × loops,
minus the same for its children. In parallel plans a node runs once in each worker process, so self times are
summed CPU time and can add up to more than the wall-clock time.
4.8 Queries with parameters
Applications usually send WHERE customer_id = $1 and pass the value separately. pg_stat_statements stores
this normalized form. Without a concrete value, EXPLAIN ANALYZE cannot run the query, but since PostgreSQL 16,
EXPLAIN (GENERIC_PLAN) can still plan it with average estimates. qopt uses that as a fallback: validation then
compares estimated costs only, and says so.

CHAPTER 5
LLMs,embeddings and RAG:just enough
qopt uses a large language model to propose fixes, and a small search engine over the
PostgreSQL manual to ground those proposals. This chapter explains the handful of ideas
involved, and why every model answer is treated as a hypothesis.
5.1 What a large language model is
A large language model (LLM) such as Google’s Gemini is a neural network trained on huge amounts of text to
predict the next piece of text. You give it a prompt (instructions plus data) and it continues. Text is processed in
tokens, pieces of words; the W13 analysis used about 3,000 input and 530 output tokens across two calls.
Temperature controls randomness: qopt uses 0.2, low but not zero, so answers are focused yet can differ
between runs.
Because the model has read a great deal about PostgreSQL, its advice is often right. But it has no way to check
itself: it has never seen your data, cannot run your query, and can be confidently wrong.

Free-form text is hard for a program to use. qopt asks Gemini to answer in JSON that follows a JSON Schema: a

“Matches the schema” still does not mean “valid SQL”, which is why the answer then goes through PostgreSQL’s
parser and, eventually, PostgreSQL itself.

facts in front of it. qopt retrieves six excerpts of the manual for the PostgreSQL version being tuned, labels them
D1…D6, and asks Gemini to cite the ones it used. The citations appear in the web UI as links to postgresql.org.
Chapter 12 explains how the documents are prepared, and Chapter 30 discusses what RAG did, and did not,

CHAPTER 6
The tools that make verification possible
qopt’s value depends on four pieces of PostgreSQL machinery. Two of them observe the
workload; two provide ground truth.
6.1 pg_stat_statements: what is slow, in aggregate
This extension (it ships with PostgreSQL) keeps running totals for every distinct statement: how often it ran
( calls ), total and mean execution time, rows returned, and page reads. Statements that differ only in their
constant values are grouped: WHERE customer_id = 42 and = 43 both become WHERE customer_id = $1 ,
identified by a 64-bit hash called the queryid . Sorting by total time answers “what should I fix first?”: a 5 ms
query called a million times matters more than one 2-second report.
6.2 auto_explain: the real plans
pg_stat_statements does not keep plans or parameter values. auto_explain (also bundled) fills the gap: when a
statement runs longer than a threshold, it writes the actual execution plan to the server log, with the full query text
including the real values. qopt configures it to log in JSON, with the same query_id , so the two sources can be
joined. The threshold is 5 ms for the demo; on a production system you would use 100 ms or more.
6.3 HypoPG: hypothetical indexes
Building a real index on a large table takes time, locks the table against writes (unless built CONCURRENTLY ) and
uses disk. HypoPG is a third-party extension that creates hypothetical indexes: entries that exist only in the
current session’s planner. Plain EXPLAIN then shows whether the planner would use the index, and how the
estimated cost changes, in milliseconds and without touching disk.

8.2 Which plan is “the baseline”?
The pipeline uses the best evidence available, in this order:
1. shadow-analyze: a real EXPLAIN ANALYZE on the shadow (median of 5). This is the normal case, and the only
one that gives timings for validation to compare against.
2. auto_explain: the real plan captured on the target, if there is no shadow.
3. target-explain or target-generic: estimates only, when the query has $1 placeholders and no captured
values.
The source is shown next to the baseline in the CLI and the UI, so you always know whether a number was
measured or estimated.

9.1 Finding the most expensive statements
qopt asks pg_stat_statements for the top statements by total execution time in the current database. It filters out
noise:
its own statements: every query qopt sends to the target starts with the comment /*qopt*/ , and those are
excluded;
catalog and monitoring queries (anything touching pg_catalog , pg_stat_* , hypopg …);
anything that is not a top-level SELECT , WITH , INSERT , UPDATE or DELETE .
9.2 Reading plans from the server log
On the target, auto_explain writes each slow execution as one JSON line in the server’s log file
( log_destination = jsonlog ). Rather than reading files from disk, which would not work for a remote or Docker
server, qopt reads them through SQL:
pg_ls_logdir() lists the newest three .json log files;
pg_read_file(path, offset, length) reads at most the last 32 MB of them;
each line is parsed. Lines from qopt’s own sessions (application name qopt-… ) are skipped, and the message
field (“ duration: 10.227 ms plan: {…} ”) yields the duration, the literal query text and the plan.
For each query id, the slowest sample is kept: it is the most representative of the problem.

The candidate’s index is built for real inside a transaction. qopt finds the new index by comparing the table’s index
list before and after, and records its real size. Expression indexes are followed by ANALYZE , because PostgreSQL
only gathers statistics on the indexed expression then. The query is then measured exactly like the baseline: one
warm-up run to load pages into memory, then five timed EXPLAIN ANALYZE runs. The median execution time is
compared with the baseline median, and the candidate passes if the planner used the new index and the time
dropped by at least 15% ( QOPT_MIN_TIME_GAIN ).
BEGINNER NOTE
Why the median, and why a warm-up? The first run of a query may read pages from disk that later runs find
in memory. And any single run can be slowed by something else happening on the machine. The median of
five is robust to one or two outliers.
GIN and trigram indexes skip Gate 2, because HypoPG cannot simulate them, and go straight to the shadow.

10.4 Thresholds and ranking
An accepted candidate gets a score: its percentage improvement (measured time, or estimated cost if no timing
was possible), minus penalties for index size relative to the table (up to 20 points) and for tables with many more

at −99.5% ranks above a composite index at −99.4%: both are dramatic, but the partial index is much smaller.

10.5 Statistics and settings
Extended statistics: on the shadow, CREATE STATISTICS + ANALYZE , then five timed runs. Accepted if the
worst row-estimate error on that table at least halves (or the query gets 15% faster), unless it made the query
more than 25% slower. For W11 the error went from 14× to 1.8×, although the time barely moved: better
estimates are valuable even when this particular plan does not change.
Settings: SET LOCAL (which lasts only until the end of the transaction), then timing. Accepted only on a 15%
gain; the result also records whether a disk spill disappeared.

records which model actually answered each call. The evaluation can pin a single model with --model , so that
configurations are compared on equal terms.
Every successful answer is cached on disk, keyed by a hash of the model, the instructions, the conversation and
the schema. The same prompt never costs a second call. Answers are parsed and validated before being cached,
so a malformed answer is never replayed.

12.2 Chunking
Each page is split along its section headings into chunks of about 1,400 characters (never more than 2,000). Each
chunk keeps the page title, its section heading, and a link to the section’s anchor, so a citation opens the exact
section. Navigation bars are dropped, as are long reference tables (more than 15 rows, such as operator-class
listings), which drowned out prose in early tests. The result is 459 chunks.
12.3 Embeddings and storage
Chunks are embedded with gemini-embedding-001 using the task type RETRIEVAL_DOCUMENT , and questions with
RETRIEVAL_QUERY . The model returns 3,072 numbers by default; qopt asks for 768, because pgvector’s HNSW
index supports at most 2,000 dimensions for the vector type. Texts are sent in batches of 50. The free tier allows
100 texts per minute, so ingestion waits when the server says so. Each chunk is stored in doc_chunks with a
generated tsvector (GIN index) and its vector(768) (HNSW index).

12.4 Hybrid search
Each finding has a built-in search phrase ( SORT_SPILL → “work_mem sort external merge disk memory”). Up
to five distinct phrases are used, plus one built from SQL keywords in the query ( ORDER BY , ILIKE , @> …).
For each phrase, the 20 best keyword matches and the 20 nearest vectors are fetched. The keyword query
ORs the words together, because requiring every word of a long phrase would match nothing.
All lists are fused with RRF ( k = 60 ). At most two chunks per section are kept, for variety, and the top six
become D1…D6.
It works without a Gemini key too: then only keyword search runs. Two real retrievals: “extended statistics
functional dependencies row estimation” returns sections 14.2.2.1 and 68.2.1 on functional dependencies and the
CREATE STATISTICS parameters; “work_mem sort external merge disk memory” returns 19.4.1 (Resource
Consumption: Memory) and the EXPLAIN ANALYZE section.
12.5 What RAG did, and did not, do
In the evaluation, the RAG configuration had the best precision (70%) and speedup (5.7×). But the difference is
small enough to be noise, and when we checked which excerpts were retrieved for the one query it uniquely
solved (W10), they were about covering and multicolumn indexes, not time zones. The honest conclusion is that
retrieval works (the excerpts are relevant, and they are cited), but its effect on outcomes is not demonstrated by
one run of 15 queries. Chapter 30 discusses this further.

CHAPTER 13
The safety model
qopt runs model-written SQL against databases. It is safe because of several independent
layers, each of which would block most problems on its own.
1
Nothing is applied for you
Recommendations are printed as CREATE INDEX CONCURRENTLY … You decide what reaches production.
2
The target is read-only
default_transaction_read_only + statement_timeout. Only catalog reads, logs, plain EXPLAIN and session-local HypoPG.
3
Every statement is parsed first
The real Postgres parser checks the statement type: no UNIQUE, no DML, no SELECT INTO or row locks, no blocked functions.
4
Experiments are sandboxed
Every shadow experiment runs inside BEGIN … ROLLBACK. DML baselines run in savepoints.
5
Rewrites run read-only
transaction_read_only is switched on before any model-written SQL runs; statement_timeout applies.
6
Sample values can be redacted
QOPT_REDACT_VALUES keeps most_common_vals (real data) out of LLM prompts.
Figure 24. Defence in depth. The outer layers limit what can reach a database at all; the inner layers limit what a statement can do
once it runs.
Layer What it prevents
1 · No automatic
changes
A good-looking but harmful change reaching production. You apply recommendations yourself, with
CONCURRENTLY so tables stay writable while the index builds.
2 · Read-only
target
Any write to the tuned database. Its sessions are opened with default_transaction_read_only = on
and a 30-second statement_timeout . EXPLAIN ANALYZE is never run there.
3 · Parser checks A model disguising a DROP or DELETE as an “index”, a rewrite that modifies data through a CTE, or calls
to dangerous functions. A test feeds in DROP INDEX orders_pkey labelled as an index and checks that it
is rejected.
4 · Sandboxed
experiments
Leftovers on the shadow: every experiment ends in ROLLBACK , and an integration test checks that the
number of indexes is unchanged afterwards.
5 · Read-only
rewrites
A rewrite writing data even if it slipped past the parser: the transaction is switched to read-only before
model SQL runs.
6 · Redaction Real values leaking into prompts: QOPT_REDACT_VALUES=true omits the most-common-value lists from
what is sent to Gemini. This matters on the free tier, where prompts may be used by Google.

14.7 Design choices worth knowing
TypeScript everywhere. The engine, CLI, API and UI share one set of types. When a field is added to
ValidationResult , the compiler points to every place that must change, including the React components.
The real parser, not regular expressions. Safety checks have to be exact: a regular expression cannot reliably
tell a harmless SELECT from one that deletes rows inside a CTE. The PostgreSQL parser can.
No ORM. The project’s job is to reason about SQL, so it writes SQL directly, always with parameters ( $1 ) for
values.
Vectors inside PostgreSQL. pgvector means no extra service to run, and documentation search uses the same
tools as everything else.
A provider interface for the LLM. The pipeline depends on a two-method interface ( LlmProvider ), not on
Gemini. The tests plug in a scripted fake model; another provider could be added the same way.

The harness analyses each query under each configuration, then applies every configuration’s top picks together

28.7 Using it on your own database
1. Set TARGET_URL to your database, and SHADOW_URL to a restored copy (for a small database,
qopt shadow sync copies it with pg_dump | psql ).
2. On the target: shared_preload_libraries = 'pg_stat_statements,auto_explain' , compute_query_id = on ,
auto_explain.log_format = json , log_destination = jsonlog , a realistic auto_explain.log_min_duration
(100 ms or more), and CREATE EXTENSION hypopg .
3. Reading logs through SQL requires superuser, or the pg_read_server_files and pg_monitor roles.
4. Set QOPT_REDACT_VALUES=true so real data values are not sent to Gemini.

Validation is the difference between 1.3× and 5.2×. “LLM, no validation” and “LLM + validation” are scored on
the same first answers. Applied blindly, those answers included SET work_mem = '64MB' for W13, the heaviest
query, which measured slower (707 → 749 ms). Validation rejected it, and the reasons fed back produced the
index that cut W13 to 150 ms.
The LLM’s value shows on queries that need a rewrite. Without RAG, Gemini produced the NOT EXISTS
rewrite for W09 (25.8 → 0.04 ms). The RAG run produced a correct time-zone-aware range rewrite for W10
(20.1 → 0.10 ms). The rule-based advisor can solve neither. But each LLM configuration solved only one of the
two: model output varies between runs.
On the standard index cases, the small model only matches the rules, and it proposes larger indexes (140 MB
for the heuristic, versus 232–256 MB).
RAG’s effect is within noise. The best precision and speedup came with RAG, but the excerpts retrieved for
W10 were not about time zones, so that win cannot be credited to retrieval. Telling them apart would need
repeated runs.

30.4 How much to trust these numbers
15 queries and one run per configuration is a small sample; differences of a few percentage points are noise.
The data is synthetic and designed to contain known problems; real workloads are messier.
All three servers ran on one laptop, so timings include some noise; medians and thresholds absorb most of it.
The LLM rows used a lite model because of free-tier quotas; a stronger model may do better, especially on
rewrites.

CHAPTER 31
Limitations and future work
31.1 Known limitations
Equivalence is tested, not proven. Two queries can agree on today’s data and differ tomorrow. The quality of
the shadow’s data bounds the strength of the check.
Changes are validated one at a time. The evaluation measures their combined effect, but an analysis does not,
and changes can interact (W11, W12).
HypoPG estimates only. Its cost gate filters quickly but can reject real wins (the W11 composite index).
Lowering QOPT_MIN_COST_GAIN sends more candidates to real timing, at the cost of more experiments.
Timing noise. A busy machine can flip borderline verdicts. The median of five and the 15% threshold absorb
most of it.
Queries without a captured sample get estimates only, because there are no parameter values to time with.
Write costs are estimated, not measured. The score penalizes indexes on write-heavy tables, but qopt does
not replay writes to measure the slowdown.
The shadow must resemble production. Different data or statistics mean different plans, and timings that do
not transfer.
31.2 Ideas for future work
Repeated evaluations over several seeds and models, with confidence intervals, to settle questions like “does
RAG help?”.
Workload-level index selection: choose the smallest set of indexes that serves many queries (W13’s index
also fixed W12), and weigh it against measured write overhead.
Validate change sets together before recommending them, not only in the evaluation.
Better shadows: copy planner statistics into a schema-only shadow (PostgreSQL 18 can export and import
statistics), or use copy-on-write database branches for realistic data at low cost.
Formal equivalence for simple rewrites, using an SQL equivalence checker alongside the data-based test.
Delivery: open a pull request with a migration file for an accepted recommendation, or run qopt in CI against a
staging database.
